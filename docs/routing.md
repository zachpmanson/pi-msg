# Messaging and Room Addressing (pi-msg)

This is the canonical specification for agent-authored XMPP messages and room
addressing. Enforcement lives in `bridge.go`, `xmpp.go`, and the XMPP tools
extension; the session seed is generated by `Bridge.messagingContract()`.

## Outbound messages are explicit

Assistant final text is **internal to the harness**. It is never routed or sent
automatically, in either a 1:1 or room-mode account. To send chat text, call:

```text
send_message(to, text, reply_to?)
```

Each call sends one message to one destination. As streamed `send_message`
arguments arrive, pi-msg sends a best-effort XEP-0085 `composing` state as soon
as the complete 1:1 `to` value is known. The delivered message includes `active`
to clear the typing indicator; if the body cannot be sent, pi-msg best-effort
sends a standalone `active` state. Indicator failures do not block delivery.
MUC messages do not get chat states. Multiple messages or recipients require multiple calls. Only a
successful `send_message` counts as a reply for run accounting. A successful
`send_file` upload is not a substitute for a chat reply. If a run that should
answer produces no successful `send_message`, pi-msg issues one bounded internal
recovery prompt. A final response is not a substitute for `send_message`.

By default, `to` must be the owner, a configured room, or a known occupant of a
configured room. A configured room is an allowed groupchat destination only
while configured; room membership is not bypassed by the arbitrary-JID option.
`allowArbitraryJid` is `false` by default. When enabled, it permits other
syntactically valid JIDs as peer destinations. It does not add unconfigured
rooms to the set of joined rooms.

Choose the destination from the incoming `from:` conversation JID, use
`sender:` to DM a participant in a room, or use the configured owner JID to
message the owner. A room reply intended for another agent must address that
agent by name or `@name`; otherwise the receiver may not see it.

### Threading a reply

`reply_to` is an optional stanza ID (shown as `[stanza …]` in history or in an
incoming prompt). It adds an XEP-0461 reply stamp and must refer to a message in
the same conversation as `to`. The ID must be present in live message history
or have been returned by `read_messages`. IDs are not destination aliases: use
`to` to select the conversation. A rejected or unknown ID fails the tool call
rather than silently sending an unthreaded message.

## Reading history

`read_messages(target, limit?, since?, before?)` reads a room or direct-chat
XEP-0313 archive. `target` is required; there is no implicit conversation
fallback and no `read_room` alias. Pass the owner JID for a 1:1 conversation, a
configured room JID for room history, or another peer JID when
`allowArbitraryJid: true`.

By default, readable targets are the owner and configured rooms. Other peers
require `allowArbitraryJid: true`; a room still must be configured. The default
window is the newest 30 messages (maximum 100), oldest first. `since` accepts
an RFC 3339 timestamp or a relative age such as `2h`; `before` pages older
history using the archive cursor `[id …]`.

History lines include both identifiers when available:

- `[id …]` is the archive pagination cursor for `before`.
- `[stanza …]` is the message ID for `send_message.reply_to` or
  `send_reaction.messageId`.

They are distinct IDs and must not be interchanged. Sent messages are included
and marked `[we sent]`. Reading is on demand and never sends a message.

## Room addressing and delivery

Room messages are delivered as prompts only when they address this agent.
`@name` and an unprefixed agent name both address that agent; quoted, fenced,
and inline-code text is ignored. `@everyone` addresses the room. `@free`
addresses idle agents (presence away or not yet asked to work), not agents
currently working. A mistyped name matches nobody. Unaddressed messages are not
queued for later; they remain available through `read_messages`.

An owner message naming nobody reaches free agents and agents who have spoken
in that room within the participation window. A message naming one agent or
replying to that agent's known stanza is routed only to that account; `@everyone`
reaches the whole room. Peer messages that do not address an agent are not
visible to it. The durable inbox preserves the original addressed verdict across
restarts.

An outbound room message intended as a handoff should use an explicit
`send_message(to=<configured room>, …)` and name the recipient. pi-msg warns,
at most once per peer-triggered run, if a room reply appears to address nobody;
owner-triggered reports are not warned. Messages are not blocked by this warning.

## Room-triggered prompts

A room-triggered prompt is a pointer block: it carries the room, sender, and
stanza ID but not the body. The agent retrieves the conversation with
`read_messages(target=<room>, limit=15)`. This prevents unaddressed room chatter
from entering a session indirectly through stale prompt text. The body remains
in the archive and can be inspected on demand.

## Delivery accounting and recovery

Only successful `send_message` calls count as outbound replies; `send_file` does
not suppress recovery. Runs that take multiple inbound messages but send fewer
replies receive one internal hint with
the ordered run history and stanza IDs, asking the agent to check for anything
still unanswered and use `reply_to` as appropriate. A no-op or final assistant
text does not count as a delivery. Heartbeat and reaction-ack runs may remain
silent by design.

Bridge-injected prompts and tool results use `[pi-msg: <topic>: …]` wrappers;
they are not XMPP messages. The initial session seed names the explicit tools
and the account's allowlist. On upgrade, a changed contract hash causes a
resumed session to receive the current seed rather than retaining the old
`to:`-routing instructions.
